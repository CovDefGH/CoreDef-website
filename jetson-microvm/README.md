# Jetson shell environment

This directory builds a Firecracker ARM64 guest on the Jetson. Website users get
real Bash processes inside the guest through a loopback-only relay and vsock.
The guest has one vCPU, 1 GiB RAM, a read-only root disk, no virtual network
interface, and RAM-backed writable home/tmp directories. Shell processes run as
separate UIDs 2000-2005 with resource limits and private home directories. The
`/srv/vault` FUSE mount mixes ordinary files from the directory underneath
the mount with Groq-generated names. Ordinary files retain their on-disk bytes
and take precedence over generated names. Directory names stay stable for five
minutes. A generated file body is requested from Groq each time it is opened,
held only by that open handle, and released when the handle closes; it is never
stored as a file or in a long-lived body cache.

This prototype mounts a read-only directory inside the Jetson guest. It does
not yet mount a customer website's directories or intercept unrelated SSH/RCE
sessions. Only regular files and directories in the underlay are passed through;
symlinks are not followed. Since generated bytes are not retained, a path's
size shown by `ls -l` and `fstat` is an estimate; it can differ from bytes read.
Two opens can return different contents, while reads through one open handle are
stable. FUSE remains visible in mount metadata.
If Groq is unavailable or its response fails validation, a generated file may
return an I/O error. The original files remain readable.

The Firecracker process is launched with Landlock rules restricting file access
to its own image, runtime sockets, and `/dev/kvm`, plus denying TCP connect/bind.
`landlock-launch --selftest` checks that the VMM cannot read `model.env` or
connect to host TCP. The broker accepts only listing, stat and read requests with
validated paths and has a daily model-call budget. The website's existing
password gate and shell session limits still apply.

The current website console defaults to the EC2 virtual shell on port 8024.
Set `SHELL_BACKEND_PORT=8025` in its launcher only after the Jetson guest passes
the smoke test. The new port stays on `127.0.0.1`.

## Install

1. Run `bootstrap.py` on the Jetson to fetch Firecracker v1.17.0 and the pinned,
   SHA-256-verified 2026-11-05 official ARM64 guest artifacts.
2. Download/extract Ubuntu's `libfuse3-dev` headers into `deps/` with
   `mkdir -p deps && cd deps && apt-get download libfuse3-dev && dpkg-deb -x libfuse3-dev_*.deb .`.
3. Place a `GROQ_KEY=...` line in `model.env` (mode 0600). Do not commit it.
4. Run `fakeroot sh build-guest.sh`, then `sh ensure.sh`.
5. Run `./landlock-launch /home/covdef/coredef-microvm --selftest`,
   `python3 smoke-isolation.py`, and `python3 smoke-console.py`.

`ensure.sh` is installed in the Jetson user crontab to restart the broker,
relay, and VM. The account must retain `/dev/kvm` access after reboot, ideally
through membership in the `kvm` group.

The model key remains outside the guest. The guest can identify that
virtualization is in use. This setup demonstrates interception before an
attacker reaches a real application server.

## Direct Linux mount

The same daemon also works without a VM. Build `fuse-daemon.c` with libfuse3
development headers and point it at the broker's Unix socket. Start on a test
directory owned by the mount account:

```sh
COREDEF_BROKER_SOCKET=/path/to/private/broker.sock \
  ./fuse-daemon -f -o ro,default_permissions,attr_timeout=0,entry_timeout=0,negative_timeout=0 \
  /path/to/existing-directory
```

The mount covers the given directory in place. Unmount with `fusermount3 -u`
to restore the ordinary view. Keep this mount limited to directories the
workload can already read and does not need to write. The daemon does not
preserve ACLs or extended attributes through the mount. Keep `allow_other`
disabled for direct mounts. Run `model_broker.py` as a separate account with
the same `COREDEF_BROKER_SOCKET` setting. By default its socket is mode 0600.
If the mount account differs from the broker account, grant it access to the
socket after each broker start and use a socket directory it can traverse.
Keep `model.env` in the broker account's private `~/coredef-microvm` directory.
The broker sends relative directory names and generated file names
to Groq as prompt context. It does not read the contents of ordinary files.
